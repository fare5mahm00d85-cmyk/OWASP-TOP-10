-هى ثغره بتجبر المستخدم ال مسجل دخول على تنفيد امر غير مقصود (يعنى بيتنفذ طلب هو مش عارف انه موجود اصلا او تم تنفيذه ).  الثغره بتحدث لأن المتصفح يرسل الكوكيز تلقائيًا مع الطلبات إلى نفس الموقع

* امتى اعرف ان فيه ثغره CSRF 
  -لو لقيت وظيفه بتغير البيانات او بتنفذ Action معين شكل 
     - تغيير كلمة السر
    - تغيير الإيميل
    - تغيير الدور (Role)
    - حذف User
    - تحويل فلوس
    - إضافة Admin
    - تحديث Profile  

* طريقه التفكير فى الثغره  
     -اول حاجه بشوفها فى Request  بسال نفسى  هل فيه CSRF Token لو فيه بيبقا غالبا الموقع بيبقا محمى لو مش موجود خالص يبقى فيه احتمال كبير يكون Vulnerable. 
     
     -تانى حاجه بشوف هل الـ Cookie بيتبعت تلقائى؟ لو الموقع بيعتمد على Session Cookie فقط فالمتصفح هيبعتها تلقائيًا. وده أساس هجوم CSRF. 
     
     -تالت حاجه بتشوف هل الطلب محتاج Password أو OTP؟ لو محتاج يبقا csrf مش هينفع 
     
     -رابع حاجه تجرب تعمل جرب تعمل PoC => في حالة **CSRF**، الـ PoC عبارة عن **صفحة HTML بسيطة** هدفها الوحيد هو إثبات أنه يمكن إرسال نفس الطلب من موقع آخر . بيتعمل ازاى ده من البيرب كليك يمين على Request تختار Engagement tools ومنها تختار Generate CSRF PoC     سيولد صفحة HTML  ولو عرف تغير حاجه ودخلت على الموقع واتغير يبقا تمااااام 
     
     -خامس حاجه لو لقيت Token جرب تغيره او تشيله او تستخدم واحد قديم ولو اشتغل يبقا ال التوكن ضعيف او اصلا مش بيتحقق منه 
     
     -سادس حاجه SameSite  هى ايه هو **خاصية (Attribute)** بتتحط مع الـ **Cookie**. بتقول للمتصفح امتا يبعت الكوكى  
        * وهناك تلات حالات منها 
             ا-  SameSite=None  يعنى  ابعت الـ Cookie في كل الحالات.
             ب- SameSite=Lax   اسمح بإرسال الـ Cookie في بعض الحالات، وامنعها في حالات أخرى.
             ج- SameSite=Strict لا ترسل الـ Cookie إذا كان الطلب بدأ من موقع مختلف.
    
     -سابع حاجه Check Content-Type بعض المواقع لا تستخدم النماذج التقليدية، بل تستخدم JSON. هل الـ Endpoint يقبل فقط: Content-Type: application/json ولا بيقبل حاجات تانيه شكل application/x-www-form-urlencoded   
     
     تامنا Check Referer Header بدل استخدام CSRF Token. هل الموقع يستخدم Referer  او Origin
