
---
## 1. Introduction

**Host Header Attack** هي مجموعة من الهجمات التي تستغل سوء استخدام أو سوء التحقق من قيمة `Host` داخل HTTP Request.

المشكلة الأساسية بتحصل لما التطبيق يثق في قيمة يقدر المستخدم يغيرها، ويستخدمها في عمليات حساسة مثل:

- إنشاء روابط استعادة كلمة المرور.
    
- إنشاء روابط تفعيل الحساب.
    
- تحديد الموقع أو الخدمة التي تستقبل الطلب.
    
- تكوين محتوى صفحات الويب.
    
- التعامل مع Web Cache.
    
- توجيه الطلبات إلى الخدمات الداخلية.
    
- اتخاذ قرارات متعلقة بالوصول والصلاحيات.
    

مهم: تغيير قيمة Host وحده لا يعني وجود ثغرة. لازم نثبت إن القيمة أثرت على سلوك التطبيق بطريقة غير آمنة.

---

## 2. What is the HTTP Host Header?

الـ Host Header هو HTTP Header بيحدد اسم النطاق الذي يطلب العميل الوصول إليه.

مثال:

```
GET /login HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Accept: text/html
Connection: close
```

شرح الأجزاء:

- `GET`: نوع الطلب HTTP Method.
    
- `/login`: المسار المطلوب Path.
    
- `HTTP/1.1`: إصدار بروتوكول HTTP.
    
- `Host`: اسم النطاق المطلوب.
    
- `User-Agent`: معلومات عن العميل.
    
- `Accept`: أنواع المحتوى المقبولة.
    

في HTTP/1.1، الـ Host Header مطلوب في الطلبات العادية.

### الفرق بين Host وIP وDNS

- **DNS:** يحول اسم النطاق إلى عنوان IP في الحالات المعتادة.
    
- **IP Address:** عنوان الجهاز أو نقطة الاتصال على الشبكة.
    
- **Host Header:** قيمة داخل طلب HTTP تحدد اسم المضيف المطلوب.
    
- **Virtual Host:** إعداد يسمح باستضافة مواقع متعددة على نفس السيرفر أو عنوان IP.
    

مثال:

```
example.com       → 192.0.2.10
shop.example.com  → 192.0.2.10
admin.example.com → 192.0.2.10
```

العناوين دي أمثلة توضيحية؛ ممكن المواقع الثلاثة تستخدم نفس عنوان IP، ويحدد السيرفر الموقع المناسب حسب إعداداته والطلب الوارد.

## 3. How Does a Host Header Attack Work?

الفكرة الأساسية:

1. المهاجم يرسل HTTP Request.
    
2. يغير قيمة Host أو Header مرتبط بها.
    
3. التطبيق أو أحد مكونات البنية التحتية يتعامل مع القيمة بطريقة غير آمنة.
    
4. القيمة تؤثر على إنشاء رابط أو محتوى أو توجيه الطلب.
    
5. إذا أمكن استغلال التأثير، تنتج ثغرة أمنية.
    

مثال:

الطلب الطبيعي:

```
GET / HTTP/1.1
Host: example.com
```

الطلب الاختباري:

```
GET / HTTP/1.1
Host: invalid.example
```

لو السيرفر رفض الطلب، فهذا لا يثبت أن جميع الوظائف آمنة. ولو قبله، فهذا لا يثبت وجود ثغرة؛ نحتاج نعرف كيف استخدم التطبيق القيمة.

---

## 4. Why Do Host Header Vulnerabilities Happen?

أهم الأسباب:

1. **Implicit Trust:** التطبيق يفترض أن قيمة Host موثوقة.
    
2. **Missing Validation:** عدم التحقق من النطاق المسموح به.
    
3. **Unsafe URL Generation:** إنشاء روابط كاملة اعتمادًا على Host غير موثوق.
    
4. **Proxy Misconfiguration:** إعدادات غير آمنة في Reverse Proxy أو Load Balancer.
    
5. **Untrusted Forwarded Headers:** الثقة في `X-Forwarded-Host` أو `Forwarded` دون التحقق من مصدرها.
    
6. **Inconsistent Parsing:** اختلاف تفسير الطلب بين الـ Proxy والتطبيق الخلفي.
    
7. **Cache Misconfiguration:** عدم مراعاة القيم التي تؤثر على الاستجابة عند تخزينها.
    
8. **Weak Access Control:** الاعتماد على اسم المضيف بدلًا من التحقق الحقيقي من الصلاحيات.

## 5. Types of Host Header Attacks

### A. Password Reset Poisoning

**الفكرة:** التطبيق ينشئ رابط إعادة تعيين كلمة المرور اعتمادًا على Host غير موثوق.

الطلب الطبيعي:

```
POST /forgot-password HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

username=test-user
```

التطبيق ينشئ رمزًا لاستعادة كلمة المرور ويرسل رابطًا للمستخدم.

الرابط الصحيح:

```
https://example.com/reset?token=RANDOM_TOKEN
```

لو التطبيق استخدم Host غير موثوق لإنشاء الرابط، فقد ينتج رابط على نطاق آخر.

الرابط المتأثر توضيحيًا:

```
https://attacker.example/reset?token=RANDOM_TOKEN
```

#### شروط نجاح الاستغلال

- التطبيق يستخدم Host غير موثوق في إنشاء الرابط.
    
- المهاجم يستطيع تشغيل عملية إرسال الرابط.
    
- الرابط الناتج يصل إلى المستخدم.
    
- يمكن للمهاجم الحصول على الرمز أو الاستفادة منه.
    
- لا تمنع الضوابط الأخرى الاستغلال.
    

#### التأثير

قد يؤدي الاستغلال الناجح إلى سرقة رمز استعادة كلمة المرور والاستيلاء على الحساب.

#### الحماية

- استخدام Base URL ثابت وموثوق.
    
- إنشاء رموز عشوائية محدودة الصلاحية وتستخدم مرة واحدة.
    
- ربط الرمز بالحساب المقصود.
    
- عدم الاعتماد على Host وحده في إنشاء الروابط الحساسة.
    

---

### B. Web Cache Poisoning

الـ Web Cache بيخزن بعض الاستجابات لتسريع الموقع.

ممكن يكون الكاش داخل التطبيق أو في Reverse Proxy أو CDN.

#### كيف تحدث المشكلة؟

1. التطبيق يستخدم Host أو Header غير موثوق في إنشاء الاستجابة.
    
2. قيمة غير متوقعة تؤثر على محتوى الصفحة.
    
3. الكاش يخزن الاستجابة المتأثرة.
    
4. مستخدم آخر يستقبل المحتوى المخزن.
    

مثال توضيحي لمحتوى صفحة:

```
<script src="https://example.com/static.js"></script>
```

لو التطبيق يسمح لقيمة غير موثوقة بالتأثير على رابط ملف JavaScript، فقد تتغير وجهة الملف.

لكن عشان تتحول المشكلة إلى Cache Poisoning، لازم يكون فيه خلل في طريقة التخزين أو في Cache Key يسمح بوصول الاستجابة المتأثرة لمستخدمين آخرين.

#### التأثير

- عرض روابط ضارة.
    
- توجيه المستخدمين إلى نطاقات غير موثوقة.
    
- تقديم محتوى غير صحيح أو ضار للمستخدمين.
    

#### الحماية

- تجنب إدخال Host غير موثوق في محتوى الاستجابة.
    
- ضبط Cache Key وفقًا للقيم المؤثرة في المحتوى.
    
- منع تخزين الاستجابات الحساسة عند الحاجة.
    
- اختبار الاستجابة المخزنة من خلال طلب لاحق مستقل.
    

---

### C. Virtual Host Attacks

الـ Virtual Hosting يسمح بتشغيل عدة مواقع على نفس السيرفر.

مثال:

```
www.example.com
admin.example.com
dev.example.com
```

قد يستضيف السيرفر موقعًا عامًا، ولوحة إدارة، وبيئة تطوير.

إذا كانت الإعدادات غير آمنة، فقد يستطيع المستخدم الوصول إلى موقع غير مقصود عن طريق تغيير Host.

#### ماذا نفحص؟

- اختلاف الاستجابة عند تغيير اسم النطاق.
    
- وجود صفحات افتراضية أو بيئات تطوير مكشوفة.
    
- ظهور صفحات إدارة دون صلاحيات مناسبة.
    
- اختلاف إعدادات التوجيه بين Proxy وBackend.
    

وجود موقع داخلي لا يعني تلقائيًا وجود ثغرة. المشكلة عندما يمكن الوصول إليه أو استغلاله خلافًا لسياسة الأمان.

---

### D. Routing-Based SSRF

SSRF تعني Server-Side Request Forgery.

هي ثغرة تحدث عندما يمكن التأثير على الطلبات التي ينفذها السيرفر إلى وجهات أخرى بطريقة غير آمنة.

في Routing-Based SSRF، قد يُستغل Host غير موثوق للتأثير على كيفية توجيه Reverse Proxy أو Load Balancer للطلب.

#### السيناريو

1. العميل يرسل طلبًا إلى Proxy.
    
2. الـ Proxy يحدد الوجهة بناءً على Host.
    
3. التحقق من النطاقات أو الوجهات غير كافٍ.
    
4. يمكن توجيه الطلب إلى خدمة غير مقصودة.
    

#### التأثير المحتمل

- الوصول إلى خدمات داخلية.
    
- كشف واجهات إدارية.
    
- الوصول إلى موارد لا ينبغي أن تكون متاحة عبر الإنترنت.
    

تغيير Host وحده لا يضمن الوصول إلى شبكة داخلية. يعتمد الاستغلال على بنية النظام وطريقة التوجيه والضوابط الموجودة.

#### الحماية

- Allowlist للوجهات والنطاقات.
    
- عدم السماح للعميل بتحديد الوجهة الداخلية مباشرة.
    
- ضبط قواعد الـ Reverse Proxy.
    
- فصل الخدمات الداخلية عن الخدمات العامة.
    

---

### E. Host Header Authentication Bypass

بعض التطبيقات تقيّد وظائف معينة بناءً على معلومات عن مصدر الطلب أو اسم المضيف.

إذا اعتمدت هذه القيود على Host بدلًا من التحقق الصحيح من هوية المستخدم وصلاحياته، فقد يظهر تجاوز للتحكم في الوصول.

مثال توضيحي:

```
/admin
```

قد تكون الصفحة مخصصة للمسؤولين.

لو التطبيق يعتقد أن الطلب آمن فقط لأن Host يشير إلى نطاق داخلي، دون التحقق من صلاحيات المستخدم، فقد يكون هناك خلل في Access Control.

**الحماية:** يجب التحقق من المصادقة والصلاحيات لكل وظيفة محمية، وعدم اعتبار Host وسيلة لإثبات الهوية.

---

### F. Classic Server-Side Vulnerabilities

قد تُمرر قيمة Host إلى وظائف أخرى في التطبيق.

لو القيمة وصلت إلى استعلام قاعدة بيانات أو قالب HTML أو نظام ملفات بطريقة غير آمنة، فقد تظهر ثغرات أخرى.

أمثلة:

- SQL Injection.
    
- XSS في سياقات معينة.
    
- أخطاء في تكوين الروابط.
    
- مشاكل في معالجة القوالب.
    

لكن وجود Host غير متحقق منه لا يعني تلقائيًا وجود أي من الثغرات دي؛ يجب إثبات طريقة استخدام القيمة وتأثيرها.

---

### G. Connection State Attacks

بعض أنظمة الـ Proxy تتعامل مع الاتصالات المستمرة التي تحتوي على أكثر من طلب.

لو النظام يتحقق من Host في بداية الاتصال ثم يفترض أن الطلبات التالية تستهدف نفس الوجهة، فقد تظهر اختلافات في التوجيه أو التحقق.

يحتاج هذا النوع إلى فحص سلوك الاتصال وإعدادات البروكسي، وليس مجرد تغيير Host في طلب منفرد.

---

### H. Ambiguous Requests

أحيانًا يرسل الطلب أكثر من قيمة Host أو يحتوي على صيغة يفسرها مكون بشكل مختلف عن مكون آخر.

مثال اختباري:

```
GET / HTTP/1.1
Host: example.com
Host: invalid.example
```

الأنظمة قد ترفض الطلب، أو تتعامل معه بطرق مختلفة.

اختلاف التفسير بين الـ Proxy والتطبيق الخلفي قد يؤدي إلى مشكلات أمنية، خصوصًا مع التخزين المؤقت أو التوجيه.

في الاختبارات، لا تستخدم الطلبات الملتبسة إلا في بيئة مصرح بها، وراقب كيف يتعامل كل مكون معها.

---

## 6. Host Override Headers

بعض الأنظمة تتعامل مع Headers إضافية قد تؤثر على اسم المضيف أو عنوان الطلب.

أهمها:

```
Host: example.com
X-Forwarded-Host: example.com
X-Forwarded-Server: example.com
X-Host: example.com
X-HTTP-Host-Override: example.com
Forwarded: host=example.com;proto=https
```

### X-Forwarded-Host

يُستخدم أحيانًا لنقل اسم المضيف الأصلي عبر Reverse Proxy.

### X-Forwarded-Proto

قد يُستخدم لنقل البروتوكول الأصلي مثل HTTP أو HTTPS.

### Forwarded

Header معياري يمكن أن يحمل معلومات مثل المضيف والبروتوكول والعميل الأصلي.

المشكلة ليست في وجود هذه الـ Headers، بل في الثقة في قيم يرسلها العميل دون التأكد من أن Proxy موثوقًا هو الذي أنشأها أو تحقق منها.

## 7. Testing Host Header Attacks Using Burp Suite

### Step 1: Intercept the Request

1. افتح Burp Suite.
    
2. افتح متصفح Burp.
    
3. ادخل على الموقع التجريبي.
    
4. افتح Proxy ثم HTTP history.
    
5. اختار طلبًا وأرسله إلى Repeater.
    

### Step 2: Establish a Baseline

أرسل الطلب الطبيعي وسجّل:

- Status Code.
    
- Response Headers.
    
- Response Body.
    
- Redirect Location.
    
- سلوك الجلسة.
    
- أي روابط كاملة يعرضها التطبيق.
    

### Step 3: Test an Arbitrary Host

```
GET / HTTP/1.1
Host: invalid.example
```

لاحظ هل الطلب يُرفض أم يُقبل، وهل تتغير الاستجابة.

### Step 4: Test Forwarded Headers

```
GET / HTTP/1.1
Host: YOUR-LAB-HOST
X-Forwarded-Host: invalid.example
```

قارن النتيجة بالطلب الطبيعي.

### Step 5: Test URL Generation

افحص الوظائف التي تنشئ روابط، مثل:

- Password Reset.
    
- Email Verification.
    
- Account Activation.
    
- Redirects.
    
- Invitation Links.
    

ابحث عن أي دليل على أن النطاق الناتج مأخوذ من قيمة غير موثوقة.

### Step 6: Test Cache Behavior

لو ظهر أن التطبيق يستخدم Cache:

- افحص `Age` و`Cache-Control` و`Vary` وغيرها من المؤشرات.
    
- تحقق مما إذا كانت الاستجابة مخزنة فعلًا.
    
- قارن طلبات مستقلة.
    
- تأكد من أن الاستجابة المتأثرة يمكن أن تصل إلى مستخدم آخر.
    

لا تعتمد على Header واحد لإثبات Cache Poisoning.

### Step 7: Document the Result

سجّل الطلب الأصلي، والتعديل، والاستجابة، والتأثير الأمني الذي أمكن إثباته.

## 9. Common Mistakes

1. اعتبار أي تغيير في Host ثغرة.
    
2. اعتبار ظهور قيمة Host في الصفحة إثباتًا نهائيًا للاستغلال.
    
3. افتراض أن `X-Forwarded-Host` موثوق تلقائيًا.
    
4. الخلط بين Host Header Attack وSSRF.
    
5. الخلط بين Host Header Attack وHTTP Request Smuggling.
    
6. تجاهل دور Reverse Proxy وCDN.
    
7. إثبات تغيير الاستجابة دون إثبات التأثير الأمني.
    
8. عدم الاحتفاظ بالطلب الأصلي للمقارنة.
    
9. اختبار موقع حقيقي دون تصريح.
    
10. الاعتماد على Payload واحد واعتبار عدم نجاحه دليلًا على الأمان.

## 10. Prevention and Mitigation

### Application Level

- استخدم نطاقًا ثابتًا وموثوقًا لإنشاء الروابط الحساسة.
    
- تحقق من Host باستخدام Allowlist.
    
- ارفض الطلبات التي تحتوي على Hosts غير معتمدة.
    
- لا تعتمد على Host في المصادقة أو تحديد الصلاحيات.
    
- استخدم روابط نسبية عندما يكون ذلك مناسبًا.
    

### Reverse Proxy / Load Balancer

- اسمح فقط بالنطاقات المطلوبة.
    
- احذف أو استبدل Forwarded Headers غير الموثوقة.
    
- لا تثق في معلومات الـ Proxy إلا عندما تأتي من مصدر معتمد.
    
- حافظ على اتساق التحقق بين الـ Proxy والتطبيق الخلفي.
    

### Cache

- راجع Cache Key.
    
- تجنب تخزين الاستجابات الحساسة بشكل مشترك.
    
- اختبر ما إذا كانت قيم الطلب غير الموثوقة تؤثر على المحتوى المخزن.
    

### Django Example

```
ALLOWED_HOSTS = [
    "example.com",
    "www.example.com",
]
```

في Django، تُستخدم `ALLOWED_HOSTS` لتحديد أسماء المضيفين المسموح بها. يجب ضبطها وفقًا للنطاقات الفعلية للتطبيق.

### Secure URL Generation Example

```
BASE_URL = "https://example.com"

reset_url = f"{BASE_URL}/reset?token={token}"
```

الفكرة هي استخدام عنوان موثوق من الإعدادات بدلًا من بناء الرابط باستخدام Host غير موثوق.

## 11. Writing a Vulnerability Report

لو اكتشفت ثغرة فعلية، تقريرك يجب أن يحتوي على:

**Title:** Host Header Injection Leading to Password Reset Poisoning

**Description:** يثق التطبيق في قيمة Host غير الموثوقة عند إنشاء روابط استعادة كلمة المرور.

**Affected Endpoint:** مسار وظيفة استعادة كلمة المرور.

**Steps to Reproduce:**

1. إرسال طلب استعادة كلمة المرور باستخدام حساب اختبار.
    
2. تعديل Host في بيئة الاختبار المصرح بها.
    
3. مراقبة الرابط الذي ينشئه التطبيق.
    
4. مقارنة الرابط بالنطاق الموثوق.
    
5. توثيق التأثير القابل للإثبات.
    

**Impact:** قد يتمكن المهاجم من توجيه روابط استعادة كلمة المرور إلى نطاق غير موثوق، وقد يؤدي ذلك إلى الاستيلاء على الحساب إذا أمكن الحصول على الرمز واستخدامه.

**Remediation:**

- استخدام Base URL موثوق.
    
- التحقق من Hosts المسموح بها.
    
- استخدام Reset Tokens آمنة ومحدودة الصلاحية.
    
- ضبط Proxy وForwarded Headers.
    

لا تكتب أن الاستيلاء على الحساب ممكن إلا إذا كان ذلك مدعومًا بنتائج الاختبار.

## 13. Quick Revision

- Host Header يحدد اسم المضيف المطلوب في HTTP Request.
    
- Host Header Attack تستغل الاستخدام غير الآمن لقيمة Host.
    
- تغيير Host وحده لا يثبت وجود ثغرة.
    
- Password Reset Poisoning يستهدف إنشاء روابط استعادة غير آمنة.
    
- Web Cache Poisoning يستهدف استجابة مخزنة يمكن أن تصل إلى مستخدمين آخرين.
    
- Virtual Host Misconfiguration قد يكشف مواقع أو خدمات غير مقصودة.
    
- Routing-Based SSRF قد يستغل التوجيه غير الآمن عبر Proxy.
    
- `X-Forwarded-Host` و`Forwarded` لا يُفترض الوثوق بهما تلقائيًا.
    
- Burp Repeater مناسب لتعديل الطلبات ومقارنة الاستجابات.
    
- الحماية تعتمد على التحقق من النطاقات، واستخدام إعدادات موثوقة، وضبط الـ Proxy والـ Cache.
    
- لازم تثبت التأثير الأمني قبل تصنيف النتيجة كثغرة.
    

**قاعدة تحفظها:** Host Header Attack مش مجرد تغيير اسم الموقع داخل الطلب؛ هي استغلال اعتماد التطبيق أو البنية التحتية على قيمة Host غير موثوقة بطريقة تؤدي إلى تأثير أمني حقيقي.
