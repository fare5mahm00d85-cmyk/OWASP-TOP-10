
--- 
# ما هو الـ Payload؟

الـ Payload هو:

> **البيانات التي تدخلها بهدف اختبار كيف سيتعامل التطبيق معها.**

في سياق XSS، الـ Payload قد يكون:

- نصًا عاديًا لمعرفة أين يظهر الإدخال.
- HTML لمعرفة هل يتم تفسيره.
- JavaScript داخل بيئة تدريبية لمعرفة هل وصل التنفيذ.

إذن الـ Payload ليس دائمًا كود JavaScript.

---

# الهدف من الـ Payload

الهدف ليس "تشغيل alert".

الهدف الحقيقي هو معرفة:

- أين وصلت البيانات؟
- كيف فسرها المتصفح؟
- ما هو الـ Context؟
- هل تم ترميزها؟
- هل تم تنظيفها؟

---

# دورة التفكير

```
User Input
     ↓
Application
     ↓
Response
     ↓
Browser Parsing
     ↓
Interpretation
     ↓
Result
```

السؤال دائمًا:

> **كيف فسر المتصفح الإدخال؟**

---

# مراحل بناء Payload

بدلًا من التفكير:

```
أريد Payload يعمل
```

فكر:

```
أين أنا؟

↓

ما الذى يتوقعه المتصفح؟

↓

كيف ستتم معالجة الإدخال؟

↓

ما نوع الاختبار المناسب؟
```

---

# أولًا

# Recon Payloads

Recon = استطلاع.

وهى أول Payloads تستخدمها دائمًا.

---

## الهدف

ليس تنفيذ JavaScript.

بل معرفة:

- أين ظهر الإدخال؟
- هل تغير؟
- هل تم حذفه؟
- هل تم ترميزه؟

---

## ماذا تستخدم؟

استخدم نصوصًا مميزة يسهل البحث عنها.

مثال:

```
XSS_TEST_12345
```

ثم افتح DevTools وابحث عنها داخل الصفحة.

إذا وجدتها، اسأل:

- هل ظهرت كنص؟
- هل أصبحت داخل HTML؟
- هل دخلت Attribute؟
- هل أصبحت داخل JavaScript؟

---

# ثانيًا

# HTML Payloads

الغرض منها اختبار:

> هل يتم تفسير HTML أم عرضه كنص؟

إذا أدخلت عنصر HTML داخل بيئة تدريبية، فهل سيظهر كعنصر أم سيظهر مكتوبًا كما هو؟

إذا ظهر كنص، فغالبًا يوجد Output Encoding.

---

# ثالثًا

# Attribute Payloads

الغرض:

اختبار ما إذا كانت البيانات موجودة داخل Attribute.

مثال منطقي:

إذا كان الإدخال يظهر داخل:

```
<input value="USER">
```

فأنت لا تختبر بنفس طريقة HTML Context.

---

# رابعًا

# JavaScript Payloads

تستخدم عندما يكون الإدخال داخل JavaScript بالفعل.

مثال:

```
<script>
var username="USER";
</script>
```

السؤال هنا ليس:

> "ما هو الكود الذي سأكتبه؟"

بل:

> "هل أنا داخل String؟ أم Number؟ أم Object؟"

---

# خامسًا

# CSS Payloads

إذا ظهر الإدخال داخل:

```
<style>
...
</style>
```

أو داخل:

```
style=""
```

فأنت داخل CSS Context.

وهنا قواعد التفسير تختلف عن HTML وJavaScript.

---

# سادسًا

# URL Payloads

إذا كان الإدخال داخل:

```
href=

src=

action=
```

فأنت تتعامل مع URL Context.

هنا يجب التفكير في:

- هل القيمة URL؟
- هل تم التحقق من البروتوكول؟
- هل هي Relative أم Absolute؟

---

# سابعًا

# SVG Payloads

SVG ليس مجرد صورة.

هو مستند يعتمد على XML.

وله طريقة Parsing مختلفة عن HTML في بعض الحالات.

لذلك يوجد له Context خاص به.

---

# ثامنًا

# Polyglot Payloads

Polyglot تعنى:

Payload يمكن أن يتوافق مع أكثر من Context.

هذا موضوع متقدم، وستقابله في بعض تقارير Bug Bounty والأبحاث، لكنه ليس نقطة البداية لتعلم XSS.

---

# Payload حسب الـ Context

|Context|نوع الاختبار المناسب|
|---|---|
|HTML|هل يتم تفسير HTML أم عرضه كنص؟|
|Attribute|هل القيمة داخل Attribute؟|
|JavaScript|ما نوع القيمة داخل الكود؟|
|CSS|هل الإدخال داخل CSS؟|
|URL|هل الإدخال يمثل عنوانًا؟|
|SVG|هل الإدخال داخل SVG؟|
|JSON|هل البيانات جزء من JSON؟|

---

# كيف أبنى Payload؟

اتبع هذه الخطوات:

```
1. حدد مكان الإدخال.

↓

2. اعرف الـ Context.

↓

3. افهم ماذا يتوقع المتصفح.

↓

4. اختبر كيف يتم عرض البيانات.

↓

5. بعد ذلك فقط اختر أسلوب الاختبار المناسب.
```

---

# لماذا يفشل Payload؟

ليس لأن الموقع آمن دائمًا.

قد يكون السبب:

- Context مختلف.
- البيانات تم ترميزها.
- البيانات تم تنظيفها.
- CSP يمنع التنفيذ.
- الإدخال لم يصل أصلًا إلى الصفحة.

---

# أخطاء المبتدئين

❌ تجربة نفس الإدخال في كل مكان.

❌ اعتبار عدم التنفيذ دليلًا على عدم وجود XSS.

❌ تجاهل DevTools.

❌ عدم معرفة أين انتهى الإدخال داخل الصفحة.

---

# كيف أفكر أثناء الاختبار؟

بدلًا من:

```
كيف أشغل JavaScript؟
```

فكر:

```
أين ذهبت بياناتي؟

↓

هل تغيرت؟

↓

هل أصبحت HTML؟

↓

هل أصبحت داخل Attribute؟

↓

هل أصبحت داخل JavaScript؟

↓

ما الذى يتوقعه المتصفح هنا؟
```
