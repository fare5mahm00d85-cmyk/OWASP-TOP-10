## 1. ما هي File Upload؟

File Upload معناها رفع ملف من جهاز المستخدم إلى السيرفر عن طريق موقع أو تطبيق ويب.

أمثلة:

- رفع صورة شخصية.
    
- رفع ملف PDF.
    
- رفع صورة منتج في متجر إلكتروني.
    
- رفع مرفق في نظام دعم فني.
    
- رفع ملف داخل منصة تعليمية.
    

لما المستخدم يختار ملفًا ويضغط Upload، المتصفح يرسل الملف إلى السيرفر، والسيرفر يستقبله ويتحقق منه ثم يخزنه أو يعالجه.

## 2. ما هي Unrestricted File Upload؟

Unrestricted File Upload هي ثغرة بتحصل لما التطبيق لا يفرض قيودًا أمنية كافية على الملفات المرفوعة، فيسمح بقبول ملفات غير مسموح بها أو التعامل معها بطريقة خطيرة.

مثال:  
موقع يسمح برفع الصور الشخصية فقط، لكن بسبب ضعف التحقق، يقبل ملفات أخرى قد تكون خطيرة.

المشكلة ليست مجرد قبول ملف غير معتاد؛ لازم نعرف هل القبول يؤدي إلى أثر أمني حقيقي أم لا.

أهم المخاطر:

- رفع ملفات غير مسموح بها.
    
- تخزين ملفات ضارة أو غير موثوقة.
    
- الوصول إلى ملفات لا ينبغي أن تكون متاحة.
    
- استغلال ضعف التحقق من اسم الملف أو نوعه أو مكان تخزينه.
    
- تنفيذ كود على السيرفر في بعض الظروف.
    
- استغلال برامج معالجة الصور أو المستندات إذا كانت ضعيفة أو غير محدثة.
    

## 3. كيف تعمل عملية رفع الملفات؟

تمر العملية غالبًا بالمراحل التالية:

1. المستخدم يختار ملفًا من جهازه.
    
2. المتصفح يرسل HTTP Request يحتوي على الملف.
    
3. السيرفر يستقبل الطلب.
    
4. التطبيق يتحقق من نوع الملف ومحتواه وحجمه وصلاحيات المستخدم.
    
5. إذا كان الملف مسموحًا، يحفظه التطبيق أو يعالجه.
    
6. قد يعرض التطبيق الملف أو يوفر رابطًا للوصول إليه.
    

تحدث الثغرة عندما تكون إحدى خطوات التحقق أو التخزين أو المعالجة غير آمنة.

## 4. مثال على رفع ملف باستخدام HTTP

طلب مبسط لرفع صورة:

POST /my-account/avatar HTTP/1.1  
Host: example.com  
Cookie: session=USER_SESSION  
Content-Type: multipart/form-data; boundary=----Boundary123

------Boundary123  
Content-Disposition: form-data; name="avatar"; filename="profile.jpg"  
Content-Type: image/jpeg

[FILE CONTENT]  
------Boundary123--

شرح أجزاء الطلب:

- POST: إرسال البيانات إلى التطبيق.
    
- /my-account/avatar: المسار المسؤول عن رفع الصورة في المثال.
    
- Cookie: قد تحتوي على جلسة المستخدم.
    
- multipart/form-data: طريقة إرسال الملفات والحقول معًا.
    
- name="avatar": اسم حقل رفع الملف.
    
- filename="profile.jpg": اسم الملف الذي أرسله العميل.
    
- Content-Type: النوع المعلن للملف.
    
- FILE CONTENT: البيانات الفعلية للملف.
    

المسار واسم الحقل هنا أمثلة توضيحية، وقد يختلفان من تطبيق إلى آخر.

## 5. الفرق بين Filename و Content-Type و File Content

### 5.1 Filename

هو اسم الملف الذي يرسله العميل، مثل:

profile.jpg  
document.pdf  
report.txt

اسم الملف لا يثبت أن محتواه يطابق الامتداد.

### 5.2 Content-Type

هو نوع المحتوى المعلن داخل الطلب، مثل:

image/jpeg  
image/png  
application/pdf  
text/plain

قد يستطيع العميل تغيير هذه القيمة، لذلك لا يجوز الاعتماد عليها وحدها للتحقق من الملف.

### 5.3 File Content

هو المحتوى الفعلي للملف.

يجب على التطبيق فحص المحتوى باستخدام وسائل مناسبة لنوع الملف، وليس الاعتماد على الاسم أو النوع المعلن فقط.

مثال:  
تغيير اسم test.txt إلى photo.jpg لا يحول الملف إلى صورة حقيقية.

وكذلك تغيير Content-Type إلى image/jpeg لا يثبت أن المحتوى صورة.

## 6. أشهر أنواع ثغرات رفع الملفات

### 6.1 عدم التحقق من نوع الملف

No File Validation

التطبيق يقبل الملفات دون التحقق الكافي من نوعها أو محتواها.

مثال:  
موقع مخصص لرفع الصور يقبل ملفات غير مخصصة للصور.

الخطر:  
يعتمد على كيفية تخزين الملف ومعالجته والوصول إليه.

الحماية:  
التحقق من نوع الملف ومحتواه قبل حفظه في المكان النهائي.

### 6.2 تجاوز التحقق من Content-Type

Content-Type Validation Bypass

يحدث عندما يعتمد التطبيق على Content-Type المرسل من المستخدم وحده.

المشكلة:  
المستخدم يستطيع إرسال قيمة لا تعكس حقيقة الملف.

الحماية:  
عدم الثقة في Content-Type وحده، وفحص المحتوى الفعلي باستخدام أدوات مناسبة.

### 6.3 تجاوز التحقق من الامتداد

Extension Validation Bypass

يحدث عندما تكون طريقة التحقق من امتداد الملف ضعيفة أو تختلف عن الطريقة التي يستخدمها السيرفر في تفسير اسم الملف.

أمثلة على أسباب المشكلة:

- الاعتماد على جزء غير صحيح من اسم الملف.
    
- اختلاف تفسير الامتداد بين مكونات التطبيق.
    
- إعدادات غير آمنة في السيرفر.
    
- عدم وجود سياسة واضحة للامتدادات المسموح بها.
    

الحماية:  
استخدام Allowlist للامتدادات المسموح بها، وتوليد اسم جديد للملف، وعدم الاعتماد على الامتداد وحده.

### 6.4 Path Traversal أثناء رفع الملفات

قد يستخدم التطبيق اسم الملف المرسل لتحديد مكان حفظه دون التحقق الآمن من المسار.

الخطر:  
قد يؤدي ذلك إلى حفظ الملف في مكان غير مقصود إذا كان التطبيق يسمح بالتأثير على المسار.

الحماية:

- عدم السماح للمستخدم بتحديد مسار التخزين.
    
- استخدام اسم ملف يولده السيرفر.
    
- حفظ الملفات داخل مجلد محدد وآمن.
    
- التحقق من المسار النهائي قبل التخزين.
    

### 6.5 ضعف فحص محتوى الملف

قد يحاول التطبيق التأكد من أن الملف صورة أو مستند، لكنه يستخدم فحصًا بسيطًا يمكن أن يفشل في اكتشاف ملفات غير صالحة أو محتوى غير متوقع.

الحماية:

- استخدام مكتبات موثوقة لتحليل الملفات.
    
- التحقق من بنية الملف الفعلية.
    
- إعادة إنشاء الصور عند الحاجة.
    
- تحديث مكتبات معالجة الملفات.
    
- عزل الملفات غير الموثوقة أثناء الفحص.
    

### 6.6 Race Condition في رفع الملفات

قد يحفظ التطبيق الملف قبل انتهاء فحصه، ثم يحذفه إذا اكتشف أنه غير صالح.

لو أمكن الوصول إلى الملف خلال الفترة بين الحفظ والحذف، فقد تظهر مشكلة أمنية.

الحماية:  
رفع الملف إلى منطقة مؤقتة غير متاحة للمستخدمين، وفحصه بالكامل، ثم نقله إلى مكان التخزين النهائي بعد نجاح التحقق.

## 7. ما هو Web Shell؟

Web Shell هو ملف سكربت على السيرفر يمكن الوصول إليه من خلال الويب لتنفيذ وظائف أو أوامر على السيرفر.

في بعض البيئات، قد يؤدي رفع Web Shell وتشغيله إلى Remote Code Execution (RCE).

RCE معناها أن المهاجم يستطيع تنفيذ كود عن بُعد على النظام المستهدف.

لكن رفع ملف PHP لا يعني تلقائيًا حدوث RCE.

لازم نميز بين أربع مراحل:

1. قبول الملف: التطبيق وافق على رفعه.
    
2. تخزين الملف: السيرفر حفظه.
    
3. الوصول إلى الملف: يمكن الوصول إليه عبر رابط أو مسار.
    
4. تنفيذ الملف: السيرفر يفسره ككود قابل للتنفيذ.
    

قد تنجح مرحلة ولا تنجح المراحل الأخرى.

مثال:  
لو السيرفر حفظ ملف PHP داخل مجلد يمنع تنفيذ PHP، فقد يكون الملف موجودًا لكنه لا ينفذ ككود.

## 8. كيفية اختبار File Upload باستخدام Burp Suite

يجب تنفيذ الاختبارات داخل لاب تدريبي أو نظام لديك تصريح باختباره.

### الخطوة الأولى: اكتشاف وظيفة رفع الملفات

افتح التطبيق وابحث عن وظيفة مثل:

- Upload Avatar.
    
- Upload Document.
    
- Attach File.
    

### الخطوة الثانية: مراقبة الطلب

افتح:

Burp Suite → Proxy → HTTP history

ارفع ملفًا عاديًا، ثم ابحث عن الطلب الذي يحتوي على الملف.

سجل:

- Request Method.
    
- Endpoint.
    
- Filename.
    
- Content-Type.
    
- حجم الملف.
    
- استجابة السيرفر.
    
- رابط الملف بعد الرفع، إن وجد.
    

### الخطوة الثالثة: إرسال الطلب إلى Repeater

اضغط بزر الفأرة الأيمن على الطلب، ثم:

Send to Repeater

الهدف هو دراسة الطلب وإعادة إرساله ومقارنة النتائج داخل اللاب.

### الخطوة الرابعة: فهم قواعد التحقق

حدد القيود التي يفرضها التطبيق:

- هل يسمح بصور فقط؟
    
- هل يحدد امتدادات معينة؟
    
- هل يحدد حجمًا أقصى؟
    
- هل يتحقق من المحتوى؟
    
- هل يعيد تسمية الملفات؟
    
- هل يخزنها في مكان آمن؟
    

اختبر كل قاعدة بشكل منفصل داخل اللاب.

### الخطوة الخامسة: التحقق من النتيجة

بعد الرفع، لا تعتمد على رسالة النجاح فقط.

تحقق من:

- هل تم حفظ الملف بالفعل؟
    
- هل يمكن الوصول إليه؟
    
- هل يعرضه التطبيق أم ينزله؟
    
- هل يتم التعامل معه كملف عادي أم كبرنامج؟
    
- هل تمكنت من تجاوز قيد أمني محدد؟
    

نجاح الطلب وحده لا يثبت وجود ثغرة.

## 9. أمثلة على أسئلة الاختبار

عند فحص أي وظيفة File Upload، اسأل نفسك:

1. ما أنواع الملفات المسموح بها؟
    
2. هل التحقق من الامتداد يتم على السيرفر؟
    
3. هل يعتمد التطبيق على Content-Type وحده؟
    
4. هل يتم فحص المحتوى الفعلي؟
    
5. هل يستطيع المستخدم التحكم في اسم الملف؟
    
6. هل يستطيع المستخدم التأثير على مكان التخزين؟
    
7. هل الملفات المرفوعة قابلة للتنفيذ؟
    
8. هل يستطيع مستخدم الوصول إلى ملفات مستخدم آخر؟
    
9. هل هناك حد أقصى لحجم الملف؟
    
10. هل تتم معالجة الملفات باستخدام مكتبات آمنة ومحدثة؟
    

هذه الأسئلة تساعدك على بناء خطة اختبار بدلًا من تجربة قيم عشوائية.

## 11. كيفية الحماية من Unrestricted File Upload

1. Allowlist: السماح بالامتدادات المطلوبة فقط.
    
2. Content Validation: فحص المحتوى الفعلي للملف.
    
3. Server-Generated Filenames: توليد أسماء جديدة للملفات على السيرفر.
    
4. Safe Storage: تخزين الملفات خارج مجلدات تنفيذ السكربتات، ويفضل خارج المسار العام للموقع.
    
5. Access Control: التحقق من صلاحيات المستخدم عند رفع الملفات والوصول إليها.
    
6. Size Limits: تحديد الحجم الأقصى وعدد مرات الرفع.
    
7. Safe Processing: استخدام مكتبات موثوقة ومحدثة لمعالجة الصور والمستندات.
    
8. Temporary Storage: فحص الملفات في منطقة مؤقتة قبل نقلها إلى مكان التخزين النهائي.
    
9. Safe File Delivery: إعداد طريقة عرض أو تنزيل الملفات بشكل آمن.
    
10. Logging: تسجيل محاولات الرفع غير الطبيعية ومراقبة الأنشطة المشبوهة.
    

لا توجد وسيلة واحدة تكفي للحماية؛ الأفضل تطبيق مجموعة من الضوابط معًا.

## 12. مصطلحات مهمة للحفظ

- File Upload: رفع الملفات.
    
- Unrestricted File Upload: رفع ملفات دون قيود أمنية كافية.
    
- Filename: اسم الملف.
    
- File Extension: امتداد الملف.
    
- Content-Type: نوع المحتوى المعلن.
    
- File Content: المحتوى الفعلي للملف.
    
- Allowlist: قائمة بالأنواع المسموح بها.
    
- Denylist: قائمة بالأنواع الممنوعة.
    
- Path Traversal: التلاعب بمسارات الملفات.
    
- Web Shell: سكربت يمكن استخدامه لتنفيذ وظائف على السيرفر عبر الويب.
    
- RCE: تنفيذ كود عن بُعد.
    
- Server-Side Validation: التحقق من البيانات على السيرفر.
    
- Race Condition: مشكلة ناتجة عن تداخل عمليات متزامنة.
    

## 13. الخلاصة

Unrestricted File Upload هي مشكلة أمنية تحدث عندما لا يفرض التطبيق ضوابط كافية على الملفات المرفوعة.

أهم النقاط:

- اسم الملف لا يثبت نوع محتواه.
    
- Content-Type وحده ليس دليلًا موثوقًا على نوع الملف.
    
- قبول الملف لا يعني أنه قابل للتنفيذ.
    
- خطورة الثغرة تعتمد على التخزين والمعالجة وإعدادات السيرفر.
    
- استخدم Burp Suite لفهم الطلبات واختبار القيود ومقارنة النتائج.
    
- يجب إثبات الأثر الأمني بدلًا من الاعتماد على رسالة نجاح الرفع.
    
- أفضل حماية هي التحقق من المحتوى، وتقييد الامتدادات، والتخزين الآمن، ومنع تنفيذ الملفات المرفوعة.
    

**قاعدة مهمة في Web Penetration Testing:**  
افهم رحلة الملف من لحظة اختياره حتى تخزينه وعرضه أو تنفيذه؛ لأن الثغرة قد تظهر في أي مرحلة من المراحل دي.
