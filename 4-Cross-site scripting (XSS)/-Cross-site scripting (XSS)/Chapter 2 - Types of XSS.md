
---
# ما المقصود بأنواع XSS؟

ليست كل ثغرات XSS تحدث بنفس الطريقة.

السؤال الأساسي هو:

**كيف وصل JavaScript إلى متصفح الضحية؟**

بناءً على إجابة هذا السؤال، يتم تقسيم XSS إلى عدة أنواع.

---

# الأنواع الرئيسية

```
Cross-Site Scripting

│

├── Reflected XSS

├── Stored XSS

└── DOM XSS
```

وهذه هي الأنواع التي ستقابلها في أغلب الاختبارات وبيئات Bug Bounty.

---

# أنواع أقل انتشارًا

```
Self XSS

Blind XSS

Mutated XSS

Universal XSS (UXSS)
```

سنشرحها أيضًا.

---

# قبل أن تبدأ

أي XSS تحتاج ثلاثة أشياء:

```
User Input

↓

Unsafe Processing

↓

Browser Executes JavaScript
```

إذا اختفى أي عنصر من الثلاثة فلن تحدث XSS.

---

# مقارنة سريعة

|النوع|مكان وجود البيانات|هل تُخزن؟|أين يحدث التنفيذ؟|
|---|---|---|---|
|Reflected|Request|لا|Browser|
|Stored|Database|نعم|Browser|
|DOM|Browser|غالبًا لا|Browser|

---

# أولًا

# Reflected XSS

يسمى أيضًا

```
Non-Persistent XSS
```

لأن البيانات لا تُخزن.

---

## الفكرة

الموقع يأخذ بيانات من الطلب.

ثم يعرضها مباشرة.

ثم ينتهي كل شيء.

---

### دورة العمل

```
Attacker

↓

يرسل Link

↓

Victim

↓

Request

↓

Server

↓

Response

↓

Browser

↓

JavaScript Executes
```

---

## مثال

الموقع يحتوي على صفحة بحث.

```
/search?q=phone
```

يعرض

```
Results for phone
```

كل شيء طبيعي.

---

لكن ماذا لو كانت قيمة البحث تحتوي على كود؟

الفكرة النظرية هي أن الموقع إذا أعاد عرض الإدخال كما هو داخل الصفحة بدون معالجة مناسبة، فقد يفسره المتصفح كجزء من الصفحة بدلًا من اعتباره نصًا.

---

## لماذا يسمى Reflected؟

لأن البيانات

```
Request

↓

Server

↓

Response
```

أي أنها تنعكس مباشرة داخل الاستجابة.

ولهذا يسمى

```
Reflected
```

---

## هل يتم تخزينها؟

لا.

كل شيء يحدث في نفس الطلب.

```
Request

↓

Response

↓

Done
```

---

## هل يحتاج ضحية؟

نعم.

لأن شخصًا ما يجب أن يفتح الرابط أو يصل إلى الصفحة التي تحتوي على الإدخال غير الآمن.

---

## هل يحتاج Database؟

لا.

---

## أشهر الأماكن

- Search
- Error Messages
- Contact Form
- Login Error
- URL Parameters

---

## الرسم الكامل

```
Victim

↓

Open Link

↓

GET Request

↓

Server

↓

Returns HTML

↓

Browser

↓

JavaScript Executes
```

# مميزات Reflected XSS

- لا يحتاج Database
- سريع
- منتشر
- سهل الاكتشاف نسبيًا

---

# عيوبه بالنسبة للمهاجم

- يحتاج ضحية
- يحتاج أن يزور الضحية الرابط أو الصفحة

---

# كيف تكتشفه؟

ابحث عن أي مكان يعرض مدخلات المستخدم داخل الصفحة.

مثل:

- Search
- Username
- Query Parameter

---

# ثانياً

# Stored XSS

يسمى أيضًا

```
Persistent XSS
```

---

## لماذا يسمى Persistent؟

لأن البيانات تُخزن.

---

## دورة العمل

```
Attacker

↓

Send Input

↓

Server

↓

Database

↓

Victim Opens Page

↓

Server

↓

Browser

↓

JavaScript Executes
```

---

## الفكرة

بدلًا من إعادة البيانات مباشرة،

يقوم الموقع بحفظها أولًا.

ثم يعرضها لاحقًا لكل من يزور الصفحة.

---

## أمثلة

- Comments
- Forum Posts
- User Profile
- Chat
- Reviews
- Support Tickets

---

## السيناريو

المهاجم يكتب تعليقًا.

↓

الموقع يحفظه.

↓

أي مستخدم يفتح الصفحة.

↓

يعرض الموقع التعليق.

↓

المتصفح يفسره.

↓

تنفيذ JavaScript إذا لم تتم معالجة المحتوى بشكل صحيح.

---

## هل يحتاج ضحية؟

نعم.

لكن الضحية لا تحتاج إلى الضغط على رابط خاص.

يكفي أن تفتح الصفحة التي تعرض المحتوى المخزن.

---

## هل يحتاج Database؟

غالبًا نعم.

---

## الرسم

```
Attacker

↓

Comment

↓

Database

↓

Victim

↓

Open Page

↓

Browser

↓

Execute
```

---

# لماذا Stored أخطر؟

لأنه:

- يستمر حتى إزالة المحتوى.
- قد يؤثر على عدد كبير من المستخدمين.
- لا يعتمد على إرسال رابط لكل ضحية.

---

# أشهر الأماكن

- Comments
- Posts
- Bio
- Username
- Chat
- Ticket System
- Admin Panel
- Feedback

# ثالثاً

# DOM XSS

أصعب نوع.

وأهم نوع في Bug Bounty.

---

## ما الفرق؟

في النوعين السابقين

الخادم كان يعيد البيانات.

أما هنا

الخادم قد لا يكون له أي دور في تنفيذ الثغرة.

---

## التنفيذ بالكامل داخل المتصفح.

---

## الرسم

```
User Input

↓

JavaScript

↓

DOM

↓

Execute
```

---

## ماذا يحدث؟

JavaScript الموجود في الصفحة يقرأ بيانات من المستخدم (مثل جزء من عنوان الصفحة أو قيمة أخرى)، ثم يضعها في الـ DOM بطريقة غير آمنة.

إذا كان الإدخال يحتوي على عناصر HTML أو JavaScript وتم إدخاله في مكان غير آمن، فقد يفسره المتصفح بدلاً من عرضه كنص.

---

## مثال على Source

```
location.search
```

---

## مثال على Sink

```
innerHTML
```

---

## الفكرة

```
Source

↓

JavaScript

↓

Sink

↓

Browser Executes
```

---

## هل يحتاج Database؟

لا.

---

## هل يحتاج Server؟

ليس بالضرورة.

---

## هل يحدث داخل Browser؟

نعم.

100%.

---

## لماذا هو صعب؟

لأن المشكلة قد تكون في JavaScript الموجود في الصفحة، وليس في استجابة الخادم.

---

# مقارنة

|الخاصية|Reflected|Stored|DOM|
|---|---|---|---|
|Database|❌|✅ غالبًا|❌|
|يحتاج Request جديد|✅|❌|أحيانًا|
|يحدث داخل Browser|جزئيًا|جزئيًا|✅ بالكامل|
|يحدث بسبب JavaScript في الصفحة|أحيانًا|أحيانًا|✅ دائمًا|

---

# رابعًا

# Self XSS

ليس ثغرة حقيقية غالبًا.

---

## الفكرة

المستخدم نفسه ينسخ كودًا ويشغله في Console.

```
User

↓

Console

↓

Paste

↓

Execute
```

---

لهذا يسمى

```
Self
```

---

# خامسًا

# Blind XSS

من الأنواع المهمة في Bug Bounty.

---

## الفكرة

المهاجم يرسل مدخلًا.

لكن لا يرى النتيجة بنفسه.

---

بعد ذلك

يفتح موظف الدعم أو المشرف الصفحة لاحقًا.

إذا كانت الصفحة تعرض المحتوى غير المعالج، فقد يتم تنفيذ JavaScript في بيئة ذلك المستخدم.

---

## أمثلة

- Contact Form
- Support Tickets
- Admin Dashboard
- CRM
- Internal Panel

---

# لماذا يسمى Blind؟

لأن المهاجم لا يرى التنفيذ مباشرة.

---

# سادسًا

# Universal XSS (UXSS)

نوع نادر جدًا.

---

ليس بسبب خطأ في الموقع.

بل بسبب خطأ في المتصفح نفسه.

إذا كان هناك خلل في المتصفح يسمح بتجاوز آليات الحماية، فقد يؤثر ذلك على أي موقع يفتحه المستخدم.

---

# مقارنة بين جميع الأنواع

|النوع|يحتاج Database|يحتاج ضحية|يحدث داخل Browser|
|---|---|---|---|
|Reflected|❌|✅|✅|
|Stored|✅ غالبًا|✅|✅|
|DOM|❌|✅|✅|
|Blind|✅ غالبًا|✅ (مثل Admin)|✅|
|Self|❌|المستخدم نفسه|✅|
|UXSS|❌|حسب السيناريو|بسبب خلل في المتصفح|

# أخطاء شائعة

❌ الاعتقاد أن كل XSS تكون Stored.

❌ الاعتقاد أن DOM XSS تحتاج قاعدة بيانات.

❌ الاعتقاد أن Reflected تُخزن.

❌ الاعتقاد أن أي JavaScript في الصفحة يعني وجود DOM XSS.

❌ الخلط بين مكان وصول البيانات ومكان تنفيذها.
