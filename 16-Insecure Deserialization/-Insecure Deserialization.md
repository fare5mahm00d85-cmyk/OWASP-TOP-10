## 1. ما هي Insecure Deserialization؟

**Insecure Deserialization** هي ثغرة أمنية بتحصل لما التطبيق يستقبل بيانات متسلسلة (Serialized Data) من مصدر غير موثوق، ويحوّلها مرة أخرى إلى Objects أو Structures داخل البرنامج من غير تحقق أمني كافٍ.

عشان نفهم الثغرة، لازم نعرف مفهومين أساسيين:

- **Serialization:** تحويل Object أو مجموعة بيانات إلى صيغة قابلة للتخزين أو الإرسال.
    
- **Deserialization:** إعادة تحويل الصيغة دي إلى البيانات أو الـ Objects الأصلية.
    

المشكلة مش في عملية التحويل نفسها، لكن في إن التطبيق ممكن يثق في بيانات المستخدم ويعيد بناء Objects تؤدي إلى سلوك خطير أثناء المعالجة.

**مثال بسيط:**

تخيل موقع عنده Object اسمه `User` بيحتوي على:

- اسم المستخدم.
    
- نوع الحساب.
    
- صلاحيات المستخدم.
    

الموقع يحوّل الـ Object ده إلى بيانات، ويبعتها للمتصفح. لو المستخدم قدر يغيّر البيانات، والسيرفر أعاد بناء الـ Object من غير تحقق من الصلاحيات، ممكن يحصل تلاعب في سلوك التطبيق.

> الفكرة الأساسية: البيانات اللي جاية من المستخدم ما ينفعش نعتبرها موثوقة لمجرد إنها Serialized.

---

## 2. الفرق بين Serialization و Deserialization

### Serialization

تحويل البيانات من شكلها الداخلي إلى صيغة قابلة للنقل أو التخزين.

مثال منطقي:

```
Object:
username = fares
role = user
```

بعد Serialization ممكن تتخزن في صيغة خاصة باللغة أو المكتبة المستخدمة.

### Deserialization

إعادة بناء البيانات من الصيغة المخزنة:

```
Serialized Data
       |
       v
Deserialization
       |
       v
Object
username = fares
role = user
```

لو التطبيق سمح للمستخدم بتعديل البيانات، وبعدها أعاد بناء Object حساس، ممكن يحصل تلاعب في البيانات أو استدعاء وظائف غير آمنة.

---

## 3. أمثلة على صيغ Serialization

كل لغة أو تقنية ممكن تستخدم صيغة مختلفة.

### PHP Serialization

مثال على بيانات PHP Serialized:

```
a:2:{s:8:"username";s:5:"fares";s:4:"role";s:4:"user";}
```

شرح الرموز:

- `a:2:` معناها Array فيها عنصران.
    
- `s:8:"username"` معناها String طولها 8 أحرف.
    
- `s:5:"fares"` معناها String طولها 5 أحرف.
    
- `s:4:"role"` معناها اسم الحقل الثاني.
    
- `s:4:"user"` معناها قيمة الحقل الثاني.
    

لاحظ إن أطوال النصوص جزء من الصيغة، فلازم تكون متوافقة مع البيانات.

### Java Serialization

بيانات Java Serialized ممكن تحتوي على معلومات خاصة بالكلاسات والـ Objects، وغالبًا تظهر كبايتات ثنائية بدل نص واضح.

### Python Pickle

مكتبة `pickle` بتحوّل Objects في Python إلى صيغة يمكن تخزينها أو إرسالها ثم استعادتها.

**مهم جدًا:** فكّ بيانات `pickle` غير موثوقة باستخدام `pickle.loads()` ممكن يؤدي إلى تنفيذ كود أثناء عملية فك التسلسل نفسها.

### JSON

JSON صيغة شائعة لنقل البيانات، لكنها لا تنفّذ كودًا تلقائيًا لمجرد تحويلها إلى Dictionary أو Object عادي. مع ذلك، ممكن تحصل ثغرات لو التطبيق يثق في حقول مثل `role` أو `isAdmin`، أو يستخدم بيانات JSON لاختيار Classes أو أنواع Objects خطيرة بطريقة غير آمنة.

## 4. أين تظهر الثغرة في تطبيقات الويب؟

ممكن تلاقي البيانات Serialized في أماكن متعددة، منها:

1. Cookies.
    
2. Hidden form fields.
    
3. HTTP request parameters.
    
4. بيانات محفوظة في Session أو Cache.
    
5. بيانات بتتنقل بين خدمات داخلية.
    
6. رسائل Queue أو Jobs.
    
7. APIs بتستخدم تنسيقات خاصة باللغات.
    
8. ملفات أو بيانات بيتم استيرادها من المستخدم.
    

مثال على Cookie:

```
Cookie: session=eyJ1c2VybmFtZSI6ImZhcmVzIn0=
```

القيمة دي شكلها Base64، وبعد فكها ممكن تظهر بيانات JSON مثل:

```
{"username":"fares"}
```

ده مجرد مثال توضيحي؛ **Base64 مش Serialization بالضرورة، وفك Base64 وحده مش معناه إن فيه ثغرة**.

كمان وجود Cookie قابلة للتعديل لا يعني تلقائيًا وجود Insecure Deserialization؛ لازم نفهم إزاي السيرفر بيتعامل معاها.

## 5. الفرق بين Encoding و Serialization و Encryption

المفاهيم دي مختلفة تمامًا:

### Encoding

تغيير شكل البيانات لتسهيل النقل أو التخزين، من غير ما يكون الهدف الأساسي إخفاء محتواها.

مثال: Base64.

### Serialization

تحويل Object أو Structure إلى صيغة يمكن نقلها أو تخزينها، ثم إعادة بنائها.

مثال: PHP `serialize()`.

### Encryption

تحويل البيانات إلى صيغة غير مقروءة عادةً من غير المفتاح المناسب.

مثال: AES.

### Signing

إضافة توقيع رقمي أو MAC للتحقق من سلامة البيانات ومصدرها وفقًا للمفتاح المستخدم.

**نقطة مهمة:** Base64 مش حماية أمنية، والتشفير وحده لا يضمن سلامة البيانات. التوقيع أو MAC ممكن يمنع التعديل غير المصرّح به إذا اتطبق صح، لكن الأفضل عدم الاعتماد على بيانات العميل لتحديد صلاحيات حساسة.

## 6. إزاي تحصل الثغرة؟

السيناريو العام بيكون كالتالي:

1. التطبيق يرسل بيانات Serialized للعميل أو يستقبلها منه.
    
2. المستخدم يقدر يغيّر البيانات، أو يزوّرها، أو يقدّم بيانات من مصدر غير موثوق.
    
3. التطبيق يعمل Deserialization للبيانات.
    
4. عملية إعادة بناء الـ Objects أو استخدام خصائصها تؤدي إلى سلوك غير آمن.
    
5. حسب تصميم التطبيق والكلاسات المتاحة، ممكن يحصل تلاعب بالصلاحيات أو قراءة ملفات أو تنفيذ كود.
    

لكن مش كل عملية Deserialization قابلة للاستغلال؛ نجاح الاستغلال بيعتمد على اللغة، والمكتبة، والكلاسات المتاحة، وطريقة استخدام البيانات.

## 7. أنواع التأثيرات الأمنية

### A. Privilege Escalation — رفع الصلاحيات

لو التطبيق بياخد الصلاحية من بيانات المستخدم القابلة للتعديل، ممكن المستخدم يغيّر قيمة مثل:

```
{
  "username": "fares",
  "role": "admin"
}
```

لو السيرفر وثق في `role` بدون تحقق مستقل، ممكن يحصل رفع صلاحيات.

دي مشكلة في تصميم الصلاحيات، ومش لازم تكون ناتجة عن Deserialization تحديدًا. لكن ممكن ترتبط بيها لو البيانات دي بتتحول إلى Object غير موثوق.

### B. Authentication Bypass — تجاوز تسجيل الدخول

لو التطبيق بيستنتج هوية المستخدم من Object غير موثوق من غير التحقق من صحة الجلسة، ممكن يحصل تجاوز للمصادقة.

الحماية الصحيحة: السيرفر هو اللي يتحقق من هوية المستخدم وصلاحياته، مش مجرد قيم يرسلها العميل.

### C. Arbitrary File Access — الوصول إلى ملفات غير مسموح بها

في بعض الحالات، ممكن تؤدي سلسلة من الكلاسات أو الوظائف إلى استخدام مسارات ملفات غير آمنة.

لكن ده مش تأثير تلقائي لكل ثغرة Deserialization، وبيعتمد على الوظائف المتاحة في التطبيق.

### D. Remote Code Execution (RCE)

ده من أخطر التأثيرات المحتملة.

ممكن يحصل لما عملية Deserialization تؤدي إلى استدعاء وظائف أو استخدام Objects بطريقة تسمح بتنفيذ أوامر أو كود يتحكم فيه المهاجم.

وجود Deserialization وحده مش كفاية لإثبات RCE؛ غالبًا لازم تتوفر شروط إضافية، زي Gadget Chain قابلة للاستغلال.

### E. Denial of Service (DoS)

ممكن تؤدي بيانات مصممة بشكل خبيث إلى:

- استهلاك كبير للذاكرة.
    
- استهلاك المعالج.
    
- Recursion عميق.
    
- إنشاء عدد كبير من Objects.
    
- تعطيل التطبيق أو زيادة استجابته بشكل كبير.

## 8. ما هي Magic Methods في PHP؟

في PHP، بعض الـ Methods الخاصة بتتنفذ تلقائيًا في مواقف معينة، ودي ممكن تكون مهمة في تحليل PHP Object Injection.

أمثلة مشهورة:

- `__wakeup()`: ممكن يتم استدعاؤها أثناء إعادة بناء Object باستخدام `unserialize()` في الحالات المناسبة.
    
- `__unserialize()`: تُستخدم في إصدارات PHP الحديثة لتنفيذ منطق مخصص أثناء إعادة بناء Object.
    
- `__destruct()`: تُنفّذ عند تدمير الـ Object أو انتهاء عمره وفقًا لدورة حياة البرنامج.
    
- `__toString()`: ممكن تُستدعى لما يتم استخدام Object كنص في سياق مناسب.
    
- `__call()`: ممكن تُستدعى عند محاولة استدعاء Method غير موجودة أو غير متاحة بالشكل المعتاد.
    

مش كل الـ Methods دي بتتنفذ في كل مرة، ومش كلها قابلة للاستغلال تلقائيًا. المهم إننا نعرف هل التطبيق بيستخدمها بطريقة غير آمنة.

### مثال توضيحي آمن

```
<?php
class User {
    public $username;

    public function __wakeup() {
        // مثال توضيحي: يتم استدعاء منطق عند إعادة بناء الكائن
        $this->username = (string) $this->username;
    }
}
?>
```

الكود بيوضح وجود منطق ممكن يعمل تلقائيًا أثناء Deserialization. تحويل النوع هنا مش استغلال بحد ذاته، لكن لو الـ Method كانت بتنفّذ عمليات حساسة اعتمادًا على بيانات غير موثوقة، ممكن تظهر مشكلة أمنية.

**ملاحظة:** التحقق من النوع وحده لا يثبت أن البيانات آمنة، ولا يمنع كل أنواع Object Injection.

## 9. ما هو PHP Object Injection؟

دي حالة بتحصل لما التطبيق يستخدم `unserialize()` على بيانات غير موثوقة، فيقدر المستخدم يتحكم في الـ Objects اللي بيتم بناؤها، وفقًا للكلاسات والقيود الموجودة.

مثال على استخدام PHP Serialization الطبيعي:

```
<?php
$data = [
    'username' => 'fares',
    'role' => 'user'
];

$serialized = serialize($data);
$restored = unserialize($serialized);
?>
```

المثال ده يوضح العملية الأساسية فقط، لكنه مش نمط آمن لاستقبال بيانات غير موثوقة في تطبيق حقيقي.

المشكلة بتظهر لما يتم فك تسلسل بيانات مهاجم بدل بيانات موثوقة، وخصوصًا لو التطبيق يحتوي على Classes فيها سلوك تلقائي أو وظائف حساسة.

### إيه اللي أبحث عنه أثناء المراجعة؟

- هل التطبيق بيستخدم `unserialize()` على بيانات من العميل؟
    
- هل توجد Classes بتحتوي على Magic Methods؟
    
- هل فيه Methods بتتعامل مع ملفات أو أوامر أو عمليات حساسة؟
    
- هل يمكن التحكم في خصائص الـ Objects؟
    
- هل فيه تحقق من مصدر البيانات وسلامتها؟
    
- هل ممكن الوصول إلى سلوك خطير من خلال تفاعل عدة Classes؟

## 10. ما هي Gadget Chain؟

الـ Gadget Chain هي سلسلة من الوظائف أو الـ Methods الموجودة بالفعل داخل التطبيق أو المكتبات المستخدمة، واللي ممكن تتصل ببعضها لتوصل إلى سلوك غير آمن.

غالبًا مش محتاج المهاجم يكتب Class جديدة على السيرفر؛ أحيانًا الكلاسات المطلوبة موجودة أصلًا.

### الفكرة بشكل مبسط

```
Untrusted Serialized Data
          |
          v
   Object Construction
          |
          v
   Magic Method / Gadget A
          |
          v
   Gadget B
          |
          v
   Sensitive Operation
```

مثلًا، قد تؤدي سلسلة من الـ Methods إلى عملية غير آمنة على ملف أو أمر نظام.

لكن وجود Classes كثيرة أو Magic Methods مش دليل كافي على وجود Gadget Chain قابلة للاستغلال؛ لازم نفهم تدفق التنفيذ والبيانات.

### مصطلحات مرتبطة

- **Gadget:** وظيفة أو Method يمكن الاستفادة منها كجزء من سلسلة.
    
- **Gadget Chain:** سلسلة من الوظائف التي تؤدي مجتمعة إلى تأثير أمني.
    
- **POP Chain:** اختصار Property-Oriented Programming، وهو أسلوب شائع في استغلال PHP Object Injection من خلال خصائص الكائنات وسلوك الـ Methods.

## 11. Java Deserialization

في Java، الـ Objects ممكن يتم تحويلها إلى Byte Stream باستخدام Serialization، ثم إعادة بنائها لاحقًا.

بعض التطبيقات تستخدم `ObjectInputStream` و`readObject()` لاستعادة الـ Objects.

المشكلة ممكن تحصل لو التطبيق أعاد بناء Objects من مصدر غير موثوق، وكان في الـ Classpath Classes تؤدي إلى سلوك خطير أثناء العملية.

### علامات تستحق الفحص

- وجود بيانات ثنائية غير مفهومة في الطلبات أو الكوكيز.
    
- تطبيق يستخدم Java Serialization في واجهة متاحة للمستخدم.
    
- استخدام `ObjectInputStream.readObject()` على بيانات غير موثوقة.
    
- وجود مكتبات أو Classes معروفة بسلوك حساس أثناء Deserialization.
    

وجود Java Serialization لا يثبت وحده وجود ثغرة، كما أن وجود مكتبة معينة لا يعني أن الاستغلال ممكن تلقائيًا.

### الحماية

- تجنب Java Native Deserialization للبيانات غير الموثوقة.
    
- استخدام تنسيقات بيانات أبسط عند الإمكان.
    
- تطبيق Allowlist للأنواع المسموح بإعادة بنائها إذا كان ذلك مناسبًا.
    
- تحديث المكتبات وإزالة الكلاسات غير اللازمة.
    
- عدم اعتبار فلترة الأنواع بديلًا كاملًا لتجنب Deserialization غير الموثوق.

## 12. Python Pickle

في Python، `pickle` مخصصة لحفظ واستعادة Objects.

مثال طبيعي للاستخدام مع بيانات موثوقة:

```
import pickle

data = {"username": "fares", "role": "user"}

serialized = pickle.dumps(data)
restored = pickle.loads(serialized)
```

الفرق المهم إن `pickle.loads()` مش مجرد تحويل آمن لنص إلى Dictionary؛ عملية الاستعادة ممكن تؤدي إلى تنفيذ وظائف بحسب محتوى البيانات.

**القاعدة الأمنية:** لا تستخدم `pickle.loads()` على بيانات غير موثوقة، حتى لو كانت البيانات جاية من مستخدم مسجل الدخول.

لو محتاج تنقل بيانات بسيطة، غالبًا JSON مع Schema Validation مناسب أكثر.

- سجّل الدخول بحسابك في بيئة الاختبار.

- افتح `Proxy → HTTP history`.
    
- حدّد الطلبات اللي تحتوي على Cookies أو Parameters أو بيانات غير معتادة.
    

### الخطوة الثانية: افحص القيم

ابحث عن:

- Base64 أو Encoding واضح.
    
- نصوص تشبه PHP Serialization مثل `O:` أو `a:`.
    
- بيانات ثنائية أو طويلة.
    
- أسماء Properties مثل `role` أو `username`.
    
- قيم بتتغير عند تسجيل الدخول أو تغيير إعدادات الحساب.
    

دي مؤشرات للفحص وليست إثباتًا للثغرة.

### الخطوة الثالثة: استخدم Decoder

من Burp Suite:  
`Decoder → Decode as Base64`، إذا كانت القيمة مناسبة لذلك.

بعد فك الترميز، اسأل نفسك:

- هل ظهرت بيانات JSON؟
    
- هل ظهرت صيغة Serialization خاصة بلغة؟
    
- هل البيانات مجرد Token عادي؟
    
- هل فيه توقيع أو MAC؟
    
- هل السيرفر بيقبل التغييرات ولا بيرفضها؟
    

**مهم:** لا تفترض أن أي قيمة Base64 هي Serialized Object.

### الخطوة الرابعة: قارن بين الطلبات

استخدم حسابات اختبار تملكها، وقارن الطلب قبل تغيير إعداد غير حساس وبعده.

لاحظ:

- أي قيم تتغير؟
    
- هل التغيير ظاهر في العميل أم محفوظ في السيرفر؟
    
- هل التطبيق يرفض القيم المعدّلة؟
    
- هل فيه تحقق مستقل من صلاحيات المستخدم؟

## 14. كيف أفكر في حل لاب Insecure Deserialization؟

لما تفتح أي لاب متعلق بالثغرة، اتبع المنهج ده:

1. **Identify the input:** حدّد البيانات اللي ممكن تكون Serialized.
    
2. **Decode the data:** فك الترميز المناسب لو موجود.
    
3. **Identify the format:** حدد هل هي PHP أو Java أو صيغة أخرى.
    
4. **Understand the object:** افهم الـ Properties والـ Classes المحتملة.
    
5. **Find the sink:** ابحث عن العملية الحساسة اللي ممكن تتأثر بالبيانات.
    
6. **Check the gadget path:** في حالة وجود Objects وMethods ذات صلة، افهم هل يمكن الوصول إلى سلوك خطر.
    
7. **Test the hypothesis:** اختبر الفرضية داخل بيئة اللاب بطريقة محدودة.
    
8. **Confirm the impact:** لا تعتبر مجرد تعديل Cookie دليلًا على RCE أو على وجود ثغرة.
    
9. **Document the result:** سجّل نقطة الضعف، وشروط نجاحها، وتأثيرها، وطريقة إصلاحها.
    

مش كل لاب محتاج Gadget Chain؛ بعض اللابات بتكون فكرتها مجرد التلاعب بخصائص Object أو استغلال تحقق ضعيف.

---

## 15. أشهر الأخطاء أثناء التعلم

- اعتبار Base64 دليلًا على وجود Serialization.
    
- الاعتقاد إن كل Deserialization تؤدي إلى RCE.
    
- تجاهل التوقيع الرقمي أو التحقق من سلامة البيانات.
    
- افتراض أن تعديل `role=user` إلى `role=admin` هينجح من غير مراجعة تحقق السيرفر.
    
- الخلط بين PHP Object Injection وInsecure Deserialization كمفهوم عام.
    
- افتراض أن Magic Methods كلها خطيرة.
    
- اعتبار وجود مكتبة معروفة دليلًا كافيًا على وجود Gadget Chain.
    
- تجاهل إصدار اللغة والمكتبات.
    
- تجربة Payloads عشوائية من غير فهم تدفق البيانات.
    
- نسيان إن تأثير الثغرة يعتمد على السياق والوظائف المتاحة.

## 16. طرق الحماية (Mitigation)

### أفضل الممارسات

1. **تجنب Deserialization غير الآمن:** خصوصًا عند استقبال بيانات من المستخدمين.
    
2. **استخدم تنسيقات بيانات أبسط:** مثل JSON عند الحاجة إلى نقل بيانات عادية.
    
3. **تحقق من البيانات:** استخدم Schema Validation وAllowlist للحقول والأنواع المناسبة.
    
4. **تحقق من الصلاحيات على السيرفر:** لا تعتمد على `role` أو `isAdmin` المرسلة من العميل.
    
5. **تحقق من سلامة البيانات:** استخدم توقيعًا أو MAC عند الحاجة، مع إدارة آمنة للمفاتيح.
    
6. **حدّث المكتبات:** لتقليل مخاطر السلوكيات الخطيرة المعروفة.
    
7. **قلّل صلاحيات التطبيق:** خصوصًا صلاحيات الملفات والنظام.
    
8. **استخدم Allowlist للـ Classes عند الضرورة:** مع فهم حدودها وعدم الاعتماد عليها وحدها.
    
9. **تجنب الاعتماد على Magic Methods لتنفيذ عمليات حساسة** بناءً على بيانات غير موثوقة.
    
10. **راقب الأخطاء:** ولا تعرض Stack Traces أو تفاصيل داخلية للمستخدم.
    

### أمثلة على بدائل أفضل

بدل فك بيانات `pickle` غير موثوقة، استخدم JSON لبيانات بسيطة:

```
import json

data = json.loads('{"username": "fares", "role": "user"}')

if not isinstance(data, dict):
    raise ValueError("Invalid data")

if set(data.keys()) != {"username", "role"}:
    raise ValueError("Unexpected fields")
```

المثال ده يوضح التحقق من شكل البيانات فقط. لا يزال لازم التطبيق يتحقق من الصلاحيات من مصدر موثوق، وما يعتمدش على `role` اللي جاية من المستخدم.

## 17. الفرق بين Insecure Deserialization وثغرات قريبة منها

### Insecure Deserialization vs IDOR

- **Insecure Deserialization:** المشكلة في إعادة بناء أو معالجة بيانات Serialized غير موثوقة.
    
- **IDOR:** المشكلة في السماح للمستخدم بالوصول إلى Object لا يملك صلاحية الوصول إليه.
    

ممكن يحصل تداخل، لكن كل واحدة لها سبب مختلف.

### Insecure Deserialization vs SQL Injection

- **SQL Injection:** إدخال بيانات تؤثر على استعلام SQL بطريقة غير آمنة.
    
- **Insecure Deserialization:** إدخال بيانات تؤثر على إعادة بناء Objects أو سلوكها.
    

### Insecure Deserialization vs Command Injection

- **Command Injection:** بيانات المستخدم بتدخل في أمر نظام من غير معالجة آمنة.
    
- **Insecure Deserialization:** ممكن تؤدي بصورة غير مباشرة إلى Command Injection أو RCE، لكنها مش نفس الثغرة.
    

### Insecure Deserialization vs Tampering

- **Tampering:** تعديل بيانات أو قيم.
    
- **Insecure Deserialization:** خلل في الثقة أو المعالجة أثناء إعادة بناء البيانات، وقد يبدأ بتلاعب في البيانات لكنه يحتاج ظروفًا إضافية ليتحول إلى استغلال.

## 18. مصطلحات مهمة للمراجعة

- **Object:** كيان برمجي يحتوي على بيانات وسلوك.
    
- **Class:** تعريف يحدد خصائص وسلوك Objects.
    
- **Serialization:** تحويل Object إلى صيغة قابلة للتخزين أو النقل.
    
- **Deserialization:** إعادة بناء البيانات أو Objects.
    
- **Untrusted Input:** بيانات لا يجوز الوثوق في سلامتها أو مصدرها.
    
- **Magic Methods:** Methods خاصة يتم استدعاؤها تلقائيًا في ظروف معينة.
    
- **Gadget:** Method أو وظيفة يمكن أن تدخل في سلسلة استغلال.
    
- **Gadget Chain:** سلسلة من الوظائف قد تؤدي إلى تأثير أمني.
    
- **POP Chain:** سلسلة استغلال تعتمد على خصائص Objects وسلوك Methods.
    
- **RCE:** تنفيذ كود عن بُعد.
    
- **Privilege Escalation:** رفع الصلاحيات.
    
- **DoS:** تعطيل الخدمة أو تقليل قدرتها على الاستجابة.
    
- **Allowlist:** قائمة محددة بالأنواع أو القيم المسموح بها.
    
- **Integrity:** ضمان أن البيانات لم يتم تعديلها دون اكتشاف ذلك.
    
- **Authentication:** التحقق من هوية المستخدم.
    
- **Authorization:** التحقق من صلاحية المستخدم لتنفيذ عملية.

## 19. أسئلة مراجعة سريعة

**س1: ما الفرق بين Serialization وDeserialization؟**

Serialization بتحوّل البيانات إلى صيغة قابلة للنقل أو التخزين، وDeserialization بتعيد بناء البيانات أو الـ Objects.

**س2: هل Base64 معناها إن البيانات Serialized؟**

لا. Base64 مجرد Encoding، وممكن تكون البيانات JSON أو نص عادي أو صيغة أخرى.

**س3: هل كل Insecure Deserialization تؤدي إلى RCE؟**

لا. التأثير بيعتمد على اللغة، والكلاسات، والوظائف المتاحة، وطريقة استخدام البيانات.

**س4: ما المقصود بـ Gadget Chain؟**

سلسلة من Methods أو وظائف موجودة بالفعل، ممكن تتفاعل مع بعضها لتؤدي إلى سلوك غير آمن.

**س5: ليه** `**pickle.loads()**` **خطيرة مع بيانات غير موثوقة؟**

لأن استعادة البيانات قد تؤدي إلى تنفيذ وظائف، وليس مجرد تحويل نص إلى Dictionary.

**س6: ما أهمية** `**__wakeup()**` **في PHP؟**

قد يتم استدعاؤها أثناء إعادة بناء Object، ولذلك لازم نفحص أي عمليات حساسة تنفذها اعتمادًا على خصائص غير موثوقة.

**س7: هل تعديل Cookie إلى** `**role=admin**` **يثبت وجود Insecure Deserialization؟**

لا. ممكن يكون تلاعبًا في الصلاحيات، لكن إثبات Deserialization يتطلب فهم كيفية معالجة السيرفر للبيانات.

**س8: ما أفضل حماية؟**

تجنب Deserialization للبيانات غير الموثوقة، واستخدم تنسيقات أبسط عند الإمكان، وتحقق من البيانات والصلاحيات على السيرفر.

---

## 20. الخلاصة النهائية

Insecure Deserialization هي ثغرة بتحصل لما التطبيق يعيد بناء Objects أو يعالج بيانات Serialized غير موثوقة بطريقة غير آمنة.

أهم النقاط:

- افهم الفرق بين Encoding وSerialization وEncryption.
    
- حدّد مصدر البيانات وطريقة معالجتها.
    
- افحص الـ Objects والـ Magic Methods عند استخدام PHP.
    
- افهم Gadget Chains في التطبيقات اللي تحتوي على Classes مناسبة.
    
- تذكّر أن RCE احتمال مش نتيجة تلقائية.
    
- اختبر باستخدام Burp Suite داخل بيئة مصرح بها.
    
- أفضل حماية هي تجنب Deserialization غير الآمن والتحقق من البيانات والصلاحيات على السيرفر.
